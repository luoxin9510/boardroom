# boardroom PRD

> 状态：草稿 v0.2（2026-11-16），拷问第 1 轮已定（见 §9），第 2 轮已定，第 3 轮进行中。拷问结束前不写代码。

## 1. 背景与目标

作者手上有很多买来的实体桌游。目标是把它们一款一款做成电子版：手机上能玩，以后能和朋友联机。参照的是 boardol.com 的做法（每款游戏一个纯函数规则引擎、可复现的随机数、轻量 WebSocket 房间、手机优先的网页），但定位不同：

- **只给自己和朋友用**，不公开上线。
- **代码公开，内容私有。** 公开仓库里只有引擎、服务、网页和原创测试内容；某款游戏的扫描图、卡牌数据、任务布局都只在作者本机的 Obsidian vault 里。
- **一款游戏一个 vault**，放在 `~/Documents/boardgame/<游戏名>/`，比如 `~/Documents/boardgame/zombicide-黑死病/`。

第一款：**Zombicide 黑死病（Black Plague）底盒**。

### 第一阶段定下的约束（作者 2026-11-15）

1. 先单人操控多个幸存者，跑通后再加联机。架构从第一天起按联机做：引擎跑在服务器上。
2. 服务器跑在本机 Mac 上。手机通过局域网或 Tailscale 打开网页，图片不经过任何第三方机器。
3. Obsidian 先只当资料库：服务直接读 vault 文件夹。Obsidian 插件以后再做。
4. 只做底盒，扩展（Wulfsburg、绿潮等）不做，但数据格式要留出扩展的位置。
5. 优先「先玩起来」：第一版是**辅助桌面**，不是完整的规则裁判。

## 2. 非目标

- 公开托管、账号系统、匹配。
- 在公开仓库里放任何商业游戏的图片、卡牌文字或任务布局。
- 第一阶段不做：完整的幸存者行动合法性校验、AI 幸存者、Obsidian 插件、联机多人。
- 不做通用的桌游规则 DSL。每款游戏的规则用 TypeScript 写，共用的部分抽成库。

## 3. 架构

```
~/Documents/boardgame/zombicide-黑死病/   （私有 vault）
        │ 读：图片、*.md 里的数据
        ▼
server/  本机 Node 进程
  ├─ 读 vault → 内容包（content pack）
  ├─ 跑规则引擎：apply(state, action) → { state, events }
  ├─ 存对局：种子 + 动作列表（可重放）
  ├─ 对局结束写回 vault/对局/*.md
  └─ HTTP（网页 + vault 图片）+ WebSocket
        │
        ▼
web/  手机优先的网页：棋盘、棋子、牌、骰子、回合流程
```

公开仓库结构（暂定，monorepo）：

| 目录 | 内容 |
|---|---|
| `packages/core` | 通用部分：种子随机（mulberry32）、动作日志、重放、房间协议类型 |
| `packages/zombicide` | 黑死病规则引擎、内容包格式和校验 |
| `packages/server` | 本机服务：读 vault、WebSocket、写回笔记 |
| `packages/web` | 网页客户端 |
| `fixtures/` | 原创测试内容（一块自造板、几张自造牌），测试和文档用 |

技术栈：TypeScript；npm workspaces；web 用 Vite + React，棋盘用 SVG（板子图当底图）；服务用 Node + `ws`；测试用 vitest。

### 3.1 引擎原则（照搬 BoardOL 验证过的做法）

- 状态是纯数据，可以序列化成 JSON。
- `apply(state, action)` 校验动作、改状态、返回事件列表；不合法就抛 `RuleError`，消息说人话（中文）。
- 所有随机都走状态里的种子。同样的种子加同样的动作，得到同样的局面：撤销、重放、断线恢复、写对局记录都靠这一点。
- 网页只发动作、收「状态 + 事件」，按事件播放动画。
- 第一版的「辅助桌面」也走同一套：手动摆放是一种动作（`{t:'place', ...}`），照样进日志、能撤销。

## 4. 黑死病底盒范围

> 数量以作者手上的实物为准，录入时核对。

- 地图：9 块双面板（18 面）。
- 幸存者：6 名，各有技能树（蓝、黄、橙、红四级）。
- 僵尸：行尸、狂奔者、胖子、憎恶、死灵法师。
- 牌：起始装备、普通装备、宝库装备、刷怪牌（按危险等级分档）。
- 任务书：底盒任务（教学关加若干任务）。
- 骰子、噪音标记、门、目标、刷怪点、出口等。

## 5. 内容包：vault 里的格式（提案，待拷问）

一切内容都是 markdown 笔记加图片，人能读、能在 Obsidian 里直接改。

### 5.1 板子 `板子/1R.md`

```markdown
---
type: tile
id: 1R
image: 1R.jpg
grid: 3x3          # 板子按 3×3 格划分；区域由格子组成
---
| 区域 | 格子 | 类型 | 备注 |
|---|---|---|---|
| a | A1 A2 | 建筑 | |
| b | A3 | 街道 | |
...
门：a|b
墙：a|c
```

区域标注是最费功夫的一步。做法待定：(1) 手写表格；(2) 网页里做一个点格子的标注工具，结果写回笔记；(3) 读图后由 agent 起草，作者核对。

### 5.2 卡牌 `卡牌/装备/装备.md`

一张 markdown 表一类牌，比如武器列：名称、张数、类型（近战/远程/法术）、射程、骰数、命中、伤害、是否噪音、双持、图片。刷怪牌一张表：每行一张牌，四列对应蓝、黄、橙、红危险等级。

### 5.3 任务 `任务/Q1 xxx.md`

frontmatter 写板子布局（板号、朝向、行列位置），正文写目标、特殊规则；地图上的门、刷怪点、目标、出口用坐标记在表里。

## 6. 功能与里程碑

### M0 骨架
- monorepo、`core` 的种子随机和动作日志、vitest。
- 服务读 `fixtures/` 里的原创测试板，网页在手机上显示地图，能摆放和移动棋子，能撤销。
- 验收：手机通过局域网打开，摆几个棋子，刷新页面后局面还在。

### M1 底盒内容
- 18 面板子入库（图片加区域标注），任务布局能加载拼出地图。
- 牌堆（洗、抽、弃、重洗）和骰子（显示每颗骰面），全部进日志。
- 幸存者卡：行动数、背包（手和背包格）、伤害、经验。
- 验收：在手机上把底盒教学任务从头玩到尾，判定靠人。

### M2 僵尸回合自动化（核心价值）
- 刷怪：按危险等级抽刷怪牌，在刷怪点放僵尸，处理额外激活、死灵法师。
- 僵尸行动：看得见幸存者就朝最近的走，看不见就朝噪音最大处走；同区就攻击；分组和分裂；狂奔者两次行动；憎恶；死灵法师逃往出口、逃脱后的后果。
- 视线和距离按区域图计算。
- 「一键僵尸回合」：逐步播放，每一步都能撤销。
- 验收：一组手写的规则案例测试全部通过；实机玩一局，僵尸回合不用手动推任何东西。

### M3 幸存者回合辅助、记录
- 行动菜单：移动、搜索、开门、近战/远程/法术攻击、交换、重整背包。系统算出合法选项并高亮，但不强制。
- 攻击：按武器数据掷骰、算命中、按目标优先级分配伤害（远程）。
- 经验条推动危险等级，技能解锁。
- 对局结束写回 `对局/YYYY-MM-DD 任务名.md`：结果、回合数、关键事件、种子和动作日志。

### 之后
- 联机：多座位，每人控制自己的幸存者；按座位权限过滤动作。
- Obsidian 插件：在 vault 里一键开局，在笔记里嵌入对局回放。
- 下一款游戏。

## 7. 风险

- **区域标注的工作量**：18 面板，每面多个区域加门墙。缓解：标注工具，或 agent 起草加人工核对。
- **规则细节多**：黑死病的僵尸规则有很多边角情况（同距离分裂、多个噪音最大处、憎恶的伤害门槛、死灵法师）。缓解：每条规则配一个案例测试；作者在 `规则/` 里写下自己的裁定。
- **手机上的操作**：小屏上点选区域和棋子。缓解：放大以区域为单位、按区域点选，不靠精确拖动。

## 8. 规则事实（来自规则书）

作者给的是英文规则书（p.2–41 + 回合摘要），要点整理在 vault 的 `规则/规则要点.md`，包括引擎必须停下来问玩家的 12 类选择。和本 PRD 相关的几条：

- 一局永远 6 名幸存者（p.6）。
- 地图规则（区域、视线、移动）都是按区域和板边直线定义的，和 3×3 网格模型一致；用实物板子核实后再定稿。
- 模型数量是规则的一部分（模型不够 → 该类僵尸额外激活），引擎要按库存计数。
- 这份 PDF **没有任务部分**（Q0–Q10），任务要另外拍照。
- 作者另有两份扩展 PDF（2026-11-16），已放进 vault 的 `扩展/`：
  - **Wulfsburg**（官方）：2 块塔楼板（10、11 号）、4 名幸存者、僵尸狼和狼憎恶、新的目标优先级、魔法装备、Ultrared 模式、9 个任务。这些任务都用底盒板加 10、11 号板，所以底盒做完后接 Wulfsburg 成本很低。
  - **In Tenebris**（粉丝自制 v2.2）：13 块板（有非正方形的长条板）、10 关战役，新增深水、深渊、树林、沼泽、石墙、通道等区域类型。说明板子模型不能写死成 3×3：每块板的网格尺寸要可配，区域类型要可扩展。卡牌数值（71 张装备、54 张僵尸牌）和 6 张角色卡也要拍照。

## 9. 决定记录

### 第 1 轮（2026-11-16，作者全部采纳推荐）

1. 板子用 3×3 网格建模，一个区域 = 若干格子，墙和门在格子边上；分不进 3×3 的板子改用更细的网格，不用多边形。
2. 技术栈：TS + Vite + React + SVG 棋盘，npm workspaces，vitest。
3. 「手动调整」动作永远保留（摆放、移除、改数值），进日志、能撤销；规则只算合法选项、做高亮，不拦人；严格模式等 M3 之后再议。
4. 撤销不改变随机结果（种子决定）；想重掷就用手动调整显式重掷，进日志。
5. 存档在 vault：`对局/存档/<日期-任务>.json`（种子 + 内容包版本 + 动作列表）；对局结束另写 `对局/<日期> <任务>.md`。
6. 界面中文；名称跟作者盒子上的一致；规则以作者手上的规则书 + 官方 FAQ 为准，`规则/裁定.md` 优先级最高。
7. 文件夹、笔记名、表格列名用中文；frontmatter 键和 ID 用英文；中文列名到字段的映射写在代码里，写错就报人话错误。
8. 默认 6 名幸存者（规则如此），开局可以选 1–6。
9. 引擎核心带「待选」状态：碰到需要玩家选的地方就暂停，只有一个合法选项时自动走；M0 就做进 `core`。
10. 竖屏手机为主：地图双指缩放平移，点区域弹出棋子和动作，幸存者卡在底部可上拉。
11. 素材由 agent 用脚本处理（透视校正、裁切、压缩），原图留在收件箱，作者在 Obsidian 里确认。
12. GitHub 公开仓库 `luoxin9510/boardroom`，MIT；每个里程碑 spec → ticket → 分支 → PR → CI 绿 → 独立 Opus 审核 → 自行合并；里程碑之间停下来等作者用手机试玩确认。

### 第 2 轮（2026-11-16，作者全部采纳推荐）

1. 盒子按英文版处理：牌名、技能名由 agent 翻成中文，笔记里写「中文名（English）」，作者可改。
2. 板子格式「默认是墙，只标例外」：每面记 9 格各属哪个区域、区域类型（建筑/街道/宝库），以及哪些格边是门（含颜色）或开口；其余边按类型推导（同区互通；不同街道区之间是分隔线，可走可看；涉及建筑的边默认是墙）。
3. 板子标注由 agent 读图起草，网页提供「标注叠加」视图供作者核对，改动写回笔记。
4. 任务由作者另外拍任务书 p.42 之后；M1 验收任务 = Q0 Danse Macabre；M0 只用原创测试板。
5. 模型库存按底盒实物计数（35/14/14/1/1），数量写在 `僵尸/` 笔记里，「模型不够 → 额外激活」照规则。
6. 待选面板预选推荐项、一点确认；每类选择有「以后都按推荐自动」开关，存在 vault 设置里。
7. 技能只做底盒 6 张角色卡上出现的，加上底盒装备的特殊效果；需要角色卡照片。
8. 只做电子骰（种子随机，逐颗显示、标命中）；实体骰用手动调整改骰面。
9. 卡牌显示照片缩略图 + 文字写出关键数值，点开看大图。
